## 1. 工具做了什么，设计目的是什么

原始 LeRobot 数据记录的是机器人**看到了什么、实测状态是什么、示教动作是什么**。这些数据本身通常没有逐帧告诉训练程序：左臂现在处于抓取还是搬运阶段、有没有拿着指定物体、当前是否具备闭合条件、合格示教接下来如何微调。

工具补充了这些人工语义标签，并记录它们的适用条件、审核状态和证据来源。它还让使用者明确选择哪些帧作为训练中心，携带中心所需的历史画面，保存动作质量审核和来源追溯信息。

大白话解释：**机器人录像是原始教材；标签是老师对某一时刻的批注；schema 是批注字典和填写规则；loss mask 则告诉训练程序，这条批注现在能不能拿来判分。** 写了批注、保存了批注、允许用它判分，是三件不同的事。

设计目的主要有四个：

1. 左右臂可以处于不同阶段，分别获得有效监督。
2. 抓取准备、释放准备等问题只在对应阶段启用，避免把不适用的问题硬标成负例。
3. 缺标、证据不足、未审核分别保存，支持逐步补标和部分字段训练。
4. 裁剪、搬移、再次导出后，仍知道每一帧来自哪里，避免时间线拼接错误和训练测试泄漏。

其中 DSE 是本项目计划训练的语义估计模块：从截至当前的图像、历史和允许的实测信息，预测阶段、抓持和局部调整等语义；这些预测未来可组织成给 VLA 的文本条件。**当前工具交付数据和读取接口，尚未实现 DSE 网络、完整训练循环或 VLA 提示接入。**

## 2. 原始数据、工作项目、导出数据的区别

| 对象              | 典型位置                               | 保存什么                                                          | 何时变化                                     |
| ----------------- | -------------------------------------- | ----------------------------------------------------------------- | -------------------------------------------- |
| 原始 LeRobot 数据 | `tron2_dataset/lerobot_v2.1_examples/` | 原始 Parquet、视频、元数据                                        | 工具只读，标注时不向里面增加文件             |
| 标注工作项目      | 启动时 `--work` 指定的目录             | SQLite 中的已保存标签、选区、规则、动作审核、偏好，以及备份和缓存 | 编辑、审核、撤销、发布 schema 时更新         |
| 导出的独立数据集  | 导出时指定的全新目录                   | 裁剪后的标准 LeRobot 数据，加 `annotations/` 附件                 | 仅代表这次导出的快照；后续编辑不会自动更新它 |

工作项目常见内容如下：

```text
my-work/
├── project.sqlite3           # 当前工作项目的数据库
├── project.sqlite3-wal       # 运行中可能存在的 SQLite 事务文件
├── project.sqlite3-shm       # 运行中可能存在的 SQLite 辅助文件
├── schemas/                 # 发布的 schema 版本文件
├── backups/                 # SQLite 备份
├── cache/                   # 视频索引、图片等可重建缓存
└── logs/                    # 运行日志
```

这里的 SQLite 是编辑阶段的事实来源。前端尚未确认的整组赋值草稿存于偏好和浏览器本地存储，**没有成为正式标签，因此不会作为正式标注导出**。已保存但未审核的 `draft` 标签会导出，其 loss mask 为 0。

导出开始时冻结已保存状态，后台按该状态生成快照，避免后续编辑混入一半结果。成功前写临时目录，通过验证后才发布到目标路径；不覆盖已有目录。

**交付训练数据应复制完整导出目录；恢复完整标注工作环境还应另外备份工作项目。** 导出附件可以重新导入继续标注，但不包含完整撤销历史、全部界面偏好、缓存和日志。

## 3. 导出目录与新增文件总览

当前导出在标准 LeRobot v2.1 结构外，增加 `annotations/` 目录中的 **9 个文件**：

```text
export_dataset/
├── meta/
│   ├── info.json
│   ├── tasks.jsonl
│   ├── episodes.jsonl
│   ├── episodes_stats.jsonl
│   └── stats.json
├── data/
│   └── chunk-000/
│       └── episode_000000.parquet
├── videos/
│   └── chunk-000/
│       ├── observation.images.cam_high/episode_000000.mp4
│       ├── observation.images.cam_left_wrist/episode_000000.mp4
│       └── observation.images.cam_right_wrist/episode_000000.mp4
└── annotations/                         # DSE 新增附件
    ├── schema.json
    ├── schema_history.json
    ├── head_spec.json
    ├── labels.parquet
    ├── samples.parquet
    ├── source_map.parquet
    ├── intervals.parquet
    ├── manifest.json
    └── validation_report.json
```

多个片段会生成多个 episode 文件；超过每个 chunk 的 episode 容量时，继续生成 `chunk-001` 等目录。相机名和路径模板以 `meta/info.json` 为准，上图采用本项目样例的名字。

| 新增文件                 | 一句话作用                            | 大白话解释                                 | 主要使用者                       |
| ------------------------ | ------------------------------------- | ------------------------------------------ | -------------------------------- |
| `schema.json`            | 当前字段、类别、适用和必填规则        | “这套标签怎么填、每个数字代表什么”         | 标注界面、规则引擎、训练接入     |
| `schema_history.json`    | 工作项目中保存的历史 schema 列表      | “以前的标签字典长什么样”                   | 追溯、重新导入                   |
| `head_spec.json`         | 当前分类头及类别输出顺序              | “模型要开几个答案栏，每栏有几个选项”       | 模型实现、类别编码               |
| `labels.parquet`         | 已展开到各帧各字段的有效标签与 mask   | “这一帧左臂这个问题的答案，能否拿来训练”   | DSE 训练、统计、检查             |
| `samples.parquet`        | 各帧角色、训练中心资格和采样权重      | “哪些帧是出题点，哪些只是随题附带的上下文” | 样本索引、采样器、数据划分       |
| `source_map.parquet`     | 新旧帧索引、源身份和媒体映射          | “裁剪后这页教材，原来在什么位置”           | 对齐、去重、防泄漏、排错         |
| `intervals.parquet`      | 区间/单帧记录、动作质量审核、事件快照 | “逐帧结果背后的区间记录和审核备注”         | 重新编辑、证据追溯、后续 BC 筛选 |
| `manifest.json`          | 格式、schema、来源、参数和文件校验和  | “本次交付的装箱单”                         | 完整性检查、复现实验             |
| `validation_report.json` | 中心监督情况、类别计数和裁剪范围汇总  | “这一批有多少可用监督、缺什么”             | 数据验收、标注排期               |

文件格式也有所区别：JSON 是一个完整对象或列表；JSONL 是每行一个独立 JSON 对象；Parquet 是有列类型、支持空值的二进制表格。可以用界面的“导出检查器”查看 Parquet，无需直接打开二进制文件。

**标准 `data/*.parquet` 中没有新塞入 `phase`、`holding` 等 DSE 类别列。** 标注单独保存在附件，靠帧键与标准数据连接，原生 LeRobot 仍可读取标准部分。

## 4. 一段数据如何变成训练中心和上下文

### 4.1 训练中心：这一帧才是要回答问题的时刻

假设使用者保留 `[150, 180)`：含 150，不含 180，即 150～179 共 30 帧。这是**训练中心区间**，不是“只保存这些帧”。

为了判断中心帧，模型可能还要看它之前的画面；为了复核 adviser，标注人员可能还要看它之后短时间的动作。因此导出同时携带前史和审核尾部。

| 位置                       | 保留目的                    | 可否作为当前片段的独立 DSE 训练样本   | 可否进入当前中心的 DSE 输入                |
| -------------------------- | --------------------------- | ------------------------------------- | ------------------------------------------ |
| 训练中心                   | 预测这一时刻的标签          | 可以；是否有有效监督还要看各字段 mask | 当前帧可以，较早中心也可能是后续中心的历史 |
| 中心之前的连续前史         | 为中心提供过去证据          | 仅上下文位置不可以                    | 按历史采样规则选中的过去帧可以             |
| 最后一个中心之后的审核尾部 | 让人查看 adviser 的后续依据 | 不可以                                | 不可以                                     |

大白话解释：要考学生“第 150 帧发生了什么”，可以给他前几帧作为题干；不能把第 155 帧的结果作为在线答题输入。题干里的图不是额外出一道题，审核人员看的后续画面也不是学生可以偷看的答案。

### 4.2 历史跨度、时刻数、保留容量是三件事

| 参数                                   |     默认值 | 含义                                     |
| -------------------------------------- | ---------: | ---------------------------------------- |
| `H = history_sampling.horizon_seconds` |     0.6 秒 | 模型最早想看到当前之前多久               |
| `T = history_sampling.num_frames`      |          4 | 每相机取多少个时刻，**包含当前**         |
| `C = context_seconds.history`          | 默认等于 H | 导出实际额外保留多少秒连续前史，可大于 H |
| `context_seconds.review`               |    0.25 秒 | 在最后一个中心后携带的审核尾部上限       |

默认目标时刻是 `t−0.6、t−0.4、t−0.2、t`，每个时刻都有三相机，合计 12 张图。`H=5、T=3` 则为 `t−5、t−2.5、t`，合计 9 张图。`H=0、T=1` 是只看当前帧。

可以一次导出保留 5 秒连续前史，默认仍用 0.6 秒/4 时刻，以便后续实验切换；只保留 0.6 秒的旧导出无法凭空提供 5 秒历史，必须回原始数据重新导出。

历史取帧使用真实时间戳，在每个目标时刻选择**不晚于该目标的最近数据行**，不跨 episode。时间戳不规则时，还可能额外保留目标之前的那一行，不能一概用 `H×FPS` 当精确行数。真实 episode 开头不足历史时，由读取器产生 padding 和存在性 mask，不复制当前图伪装成过去。

行为复核界面可以查看 0.5、1、2、5 秒等更长未来参考，**这不改变当前导出固定的 0.25 秒审核尾部，也不改变自动 adviser 候选的最多 0.25 秒窗口**。

### 4.3 不连续片段与重复帧

相邻或重叠的中心区间合并；同一来源里隔着缺口的中心形成独立新 episode，不能把缺口直接删掉后拼成连续动作。

两个独立片段的上下文可能重叠，因此同一源帧可以保存两次。它在 A 片段中是中心，在 B 片段中可能只是前史：标签值可以相同，mask 却不同。两份副本必须共享源身份和 `split_group`，不能分别落进训练集与测试集。

## 5. 标签内容：默认标注哪些事情

默认有 8 个字段，每个字段各标左臂、右臂，共 16 个“臂×字段”。字段可配置，实际训练务必读**这份导出的** `schema.json` 和 `head_spec.json`，不要把下表写死在模型里。

### 5.1 phase：当前操作阶段

| 默认 ID | key           | 中文含义               | 判断时容易混淆的地方                                      |
| ------: | ------------- | ---------------------- | --------------------------------------------------------- |
|       0 | `idle`        | 暂不参与/空闲          | 静止不自动等于 idle，暂停搬运仍可能是 transport           |
|       1 | `approach`    | 接近目标               | 尚未进入抓取局部对准区域                                  |
|       2 | `grasp_align` | 抓取对准               | 闭合前的局部调整，必须包含偏位、尚未准备好的情况          |
|       3 | `grasp_check` | 闭合与抓持检查         | 已开始实际闭合、建立/检查抓持；检查性小幅提起仍可属于这里 |
|       4 | `transport`   | 搬运                   | 有持物证据，向放置目标运动，尚未进入放置局部调整          |
|       5 | `place_align` | 放置对准               | 持物进入放置局部区域，调整位置、朝向或支撑关系            |
|       6 | `withdraw`    | 释放后撤离             | 已能确认物体留在指定承接位置，夹爪脱离并撤出              |
|       7 | `recover`     | 异常后恢复重试         | 依据当前及允许历史可见异常，正在重开、退回或重试          |
|       8 | `unknown`     | 当前证据不足以判断阶段 | 是有意义的答案，不是空白                                  |

左右臂独立，不取两臂的“最大阶段”作为共同阶段；阶段可以回退或重新进入，不是必须按 0→7 走完的流程。

阶段边界还依赖任务协议中的目标抓取部位、承接区域和最大夹爪开口宽度 W。TCP 是机械臂末端/夹爪的约定参考点；默认研究协议用“TCP 到目标抓取部位不超过 W”描述抓取局部区域，用“物体指定支撑部位到承接区域不超过 W”描述放置局部区域。W 是经标定的最大开口尺度，不是这一帧实时开度。当前工具不从未标定 RGB 自动测出这些距离；边界证据不足时允许 unknown。

### 5.2 holding：有没有持着指定目标

默认 `0=empty、1=holding、2=unknown`。

判断的是**指定目标**的可见夹持关系或与夹爪共同运动的证据。夹爪闭合不等于拿到了物体，夹到其他东西也不能当作持有指定目标。它不是抓取成功概率，也不测量隐藏的摩擦稳定性。

### 5.3 close_readiness：保持当前位置，现在闭合是否具备可见条件

默认 `0=not_ready、1=ready、2=unknown`，仅抓取对准阶段适用。

大白话解释：**先假设机械臂不再挪位置，就在现在这个姿态合拢夹爪，看可见条件是否支持这么做。** 要看指定部位是否在有效夹持区域、开口是否够、方向和高度是否合适、路径是否有阻挡、相对运动是否过大。

明确不满足条件填 not_ready；关键视角缺失、判断不了填 unknown。后面示教真的闭合了，或最终抓成功了，都不能倒推这一帧必然 ready。

### 5.4 release_readiness：保持当前位置，现在松开是否具备轻放条件

默认 `0=not_ready、1=ready、2=unknown`，搬运和放置对准阶段适用。

大白话解释：**现在不再挪机械臂，直接打开夹爪，指定物体能否按本任务的轻放协议留在正确承接区域。** 要看持物、承接位置、支撑几何、运动和脱离阻碍等证据。

默认一致性规则要求 `ready` 必须同时有 `phase=5 · place_align` 和 `holding=1`。不能因为“下一步示教松手”就标 ready。这是任务条件标签，不是对所有机器人、物体、接触力都通用的物理安全证明。

### 5.5 adviser：合格示教在短窗口里采用的局部调整

| 字段                  | 默认类别                                     | 大白话解释                                         |
| --------------------- | -------------------------------------------- | -------------------------------------------------- |
| `adviser.x`           | 0 none / 1 positive / 2 negative / 3 unknown | 接下来合格示教沿前后轴怎么调整                     |
| `adviser.y`           | 同上                                         | 沿左右轴怎么调整                                   |
| `adviser.z`           | 同上                                         | 沿上下轴怎么调整                                   |
| `adviser.orientation` | 0 keep / 1 adjust / 2 unknown                | 有没有明显调整夹爪朝向；不编码精确转轴、角度或方向 |

方向使用已核实的规范机器人基座系：`+X` 向前，`+Y` 向机器人左，`+Z` 向上。这里的左/右是机器人方向，不是屏幕左右。

**adviser 表示合格示教采用的一种短期调整方式，不能解释成当前状态唯一正确的动作，也不表示精确动作幅度。** `none/keep` 只表示该分量没有显著运动，不表示已经对准、不需要其他轴移动、应该闭合、应该松开或整个动作块必须静止。

自动候选需核实米制单位、基座系刚体变换和动作质量审核；从当前开始寻找连续 approved 前缀，最多 0.25 秒，遇到阶段变化或事件边界停止，不足 0.1 秒不给候选。显著往返平移或旋转导致净变化抵消时，受影响分量输出 unknown，而不是凭首末差编一个确定方向。当前规则版本是 `approved-displacement-2`。

自动建议被接受后仍是草稿；人工审核与“动作片段 approved”是另外两步。手动 adviser 不会自动获得与候选相同完整的坐标配置和窗口 provenance，接收数据时要单独核实证据。

| phase              | holding                        | close_readiness | release_readiness | adviser 四分量 |
| ------------------ | ------------------------------ | --------------- | ----------------- | -------------- |
| idle               | 不适用                         | 不适用          | 不适用            | 不适用         |
| approach           | 适用、必填                     | 不适用          | 不适用            | 不适用         |
| grasp_align        | 适用、必填                     | 适用、必填      | 不适用            | 适用、必填     |
| grasp_check        | 适用、必填                     | 不适用          | 不适用            | 不适用         |
| transport          | 适用、必填                     | 不适用          | 适用、必填        | 不适用         |
| place_align        | 适用、必填                     | 不适用          | 适用、必填        | 适用、必填     |
| withdraw / recover | 适用、必填                     | 不适用          | 不适用            | 不适用         |

## 6. schema.json：标签字典与规则

### 6.1 顶层字段

| 字段              | 内容                              | 作用                                                   |
| ----------------- | --------------------------------- | ------------------------------------------------------ |
| `version`         | 正整数版本号                      | 标识当前已发布规则版本；与标签审核版本、模型头版本对应 |
| `fields`          | 当前活动字段列表                  | 决定界面和导出要生成哪些字段                           |
| `retired_fields`  | 可选，`field_id → 原字段对象`     | 登记已经删除的字段，保留旧定义、禁止重新占用身份       |
| `retired_classes` | 可选，`field_id → 已删除类别列表` | 登记已删除类别，防止旧 ID 被当作新含义使用             |

schema 版本是项目内版本，两个独立项目都叫 v2，并不表示内容相同；需要结合 `schema_hash` 比较。

### 6.2 fields 中每个字段的属性

| 属性                       | 内容                                    | 大白话解释                                           |
| -------------------------- | --------------------------------------- | ---------------------------------------------------- |
| `field_id`                 | 稳定机器标识，如 `holding`、`adviser.x` | 程序连接标签和模型头用的名字，不是可随便换的显示文字 |
| `label`                    | 显示名称                                | 界面上叫什么                                         |
| `description`              | 语义和标注说明                          | 这个问题究竟在问什么                                 |
| `scope`                    | `each_arm` 或 `global`                  | 左右臂分别回答，还是整帧只回答一次                   |
| `type`                     | 当前为 `categorical`                    | 从有限类别中选择，不能把类别数字当连续物理量回归     |
| `classes`                  | 类别对象列表                            | 允许哪些答案；列表顺序还影响分类头顺序               |
| `unknown_id`               | 指向该字段某个稳定类别 ID               | 哪个答案代表“看过证据，仍判断不了”                   |
| `applicable_when`          | 布尔值或规则树                          | 什么条件下，问这个问题才有意义                       |
| `required_when`            | 布尔值或规则树                          | 什么条件下，完整标注要求必须回答这个问题             |
| `evidence`                 | `state` 或 `behavior`                   | 状态证据权限，还是允许未来的行为复核权限             |
| `independent_when_missing` | 可选，依赖引用列表                      | 声明特定依赖未填时，这个字段能否在独立审核后先使用   |

适用与必填不同：不必填的可选字段，填了且适用、审核有效，也可以训练；必填字段没填，会影响完成情况，但不应抹掉其他字段的有效监督。

`independent_when_missing` 的默认用途是 holding：phase 缺失，但当前可见证据足以独立确认持物关系时，可以先审核 holding。它不把明确 idle 的 holding 改成适用，也不会把 phase 自动补齐。

### 6.3 classes 中每个类别的属性

| 属性         | 含义                                                           |
| ------------ | -------------------------------------------------------------- |
| `id`         | 字段内稳定整数身份；不同字段的同一个数字可以代表完全不同的意思 |
| `key`        | 稳定机器语义名，如 `ready`、`unknown`                          |
| `label_zh`   | 中文显示文字                                                   |
| `color`      | 界面颜色，不是训练特征                                         |
| `shortcut`   | 界面快捷键，不是训练特征                                       |
| `deprecated` | 可选，标记废弃；不再允许新标注选择，需核实旧值的审核/版本状态  |

**删除与废弃不同。** 删除后从活动类别/模型头中移除，旧 ID 进入 retired 登记；废弃类别仍留在 `classes` 中，当前 `head_spec` 仍会列出它。训练端应按真实 head_spec 建头，不能自行过滤废弃项后仍沿用旧输出顺序。

发布新 schema 会让已有标签变为 `needs_review`，其旧审核版本不会自动变成当前版本。即使只改显示说明，也应检查当前实现造成的复核影响。

已删除字段不再出现在当前 labels 活动字段和 head_spec 中；已删除类别的旧值在当前逐帧结果里变为 `value_id=null`、`missing/needs_review`、mask=0。原始旧值仍可能在 `intervals.parquet` 中，其含义由历史 schema 和 retired 登记解释。

### 6.4 规则树怎么读

例子：

```json
{
  "field": "self.phase",
  "op": "in",
  "values": [2, 5]
}
```

意思是：“针对当前这条手臂，它的 phase 是抓取对准或放置对准时，条件成立。”

| 规则元素                               | 含义                                                        |
| -------------------------------------- | ----------------------------------------------------------- |
| `true` / `false`                       | 始终成立 / 始终不成立                                       |
| `self.<field_id>`                      | 当前手臂的字段；`self.adviser.x` 的字段名整体是 `adviser.x` |
| `left.<field_id>` / `right.<field_id>` | 明确引用左/右臂                                             |
| `global.<field_id>`                    | 引用全局字段                                                |
| `op: eq` + `value`                     | 等于某个类别 ID                                             |
| `op: ne` + `value`                     | 不等于某个类别 ID                                           |
| `op: in` + `values`                    | 属于一组类别 ID                                             |
| `all: [...]`                           | 所有子条件都要成立                                          |
| `any: [...]`                           | 至少一个子条件成立                                          |
| `not: {...}`                           | 对子条件取反                                                |

规则结果有三种：真、假、未知。父字段没填，或者父字段为 unknown 且规则没有明确把这个 unknown ID 纳入比较时，结果可能未知。

例如 phase=8 时，“phase 是否为 2”得到未知，不能当作明确 false；而 holding 的默认规则显式包含 phase=8，因此它仍适用。`all` 中有明确 false 则整体 false；`any` 中有明确 true 则整体 true；其余含未知的情况保留未知。

大白话解释：**不知道现在是不是抓取对准，不等于已经知道现在不是抓取对准。** 这就是不能把 `undetermined` 偷换成负例的原因。

状态字段不能通过规则引用未来行为字段；循环依赖、无效类别引用、占用已删除身份等也会被拒绝。phase 是当前实现的基础字段，不能删除；内置一致性规则引用的类别也不能在仍有依赖时直接删除。

## 7. schema_history.json 与 head_spec.json

### 7.1 schema_history.json

文件是一个 schema 对象列表，每项结构与 `schema.json` 相同，按版本保存。当前导出携带工作项目中保存的历史 schema，用于解释旧区间记录、删除登记和重新导入。

它是**规则版本历史**，不是每一次鼠标操作、所有旧标签值、审核员身份和时间的完整审计日志。修改后的当前区间状态保存在 intervals，完整撤销快照留在工作 SQLite 中。

### 7.2 head_spec.json

| 字段                | 含义                                                     |
| ------------------- | -------------------------------------------------------- |
| `schema_version`    | 对应当前 schema 版本                                     |
| `schema_hash`       | 对 schema 内容规范化计算的 SHA-256，防止同版本号内容不同 |
| `categorical_heads` | 当前分类头定义列表                                       |
| `note`              | 关于动态头和稳定类别 ID 的说明文字                       |

每个 `categorical_heads` 项包含：

| 字段        | 含义                                                       |
| ----------- | ---------------------------------------------------------- |
| `field_id`  | 对应标签字段                                               |
| `scope`     | `each_arm` 表示左右臂都要有对应输出；`global` 表示全局输出 |
| `classes`   | 当前类别对象及显示/语义信息                                |
| `size`      | 该字段分类输出数量                                         |
| `class_ids` | 按 logits 位置排列的稳定类别 ID 列表                       |

默认文件列出 8 个字段定义，不是列出 16 个左右臂独立条目；`each_arm` 告诉模型实现分别为两臂产生这些输出。

假设删除 adviser.x 的 ID=1，增加新类别 ID=4，当前顺序为：

```text
class_ids = [0, 2, 3, 4]
logits 下标     0  1  2  3
稳定类别 ID     0  2  3  4
```

稳定 ID=4 的答案应该对应 logits 下标 3，不能直接把 4 交给只有 4 个输出的交叉熵。类别重排也可能改变 logits 顺序。训练和 checkpoint 必须保存 schema/hash 与 class_ids；代码提供 `encode_class_targets` 做这层映射。

## 8. labels.parquet：逐帧、逐臂、逐字段标签

### 8.1 一行是什么

这是一张**长表**：一行表示“某个导出帧、某条手臂、某个字段”的结果。

```text
导出 EP0 / 帧18 / left / phase             → 一行
导出 EP0 / 帧18 / left / holding           → 另一行
导出 EP0 / 帧18 / right / phase            → 又一行
```

当前默认 schema 下，每个导出帧生成 16 行，包含中心和上下文，也包含没有填写的字段。若新增一个 `each_arm` 字段，每帧增加 2 行；新增一个 `global` 字段，每帧增加 1 行。

当前唯一连接键为 `(episode_index, frame_index, arm, field_id)`。不要只按 `frame_index` 连接，不同 episode 都有第 0 帧；也不能按源帧键合并后丢掉片段身份，因为同源副本的 mask 可能不同。

### 8.2 全部列的意义

下表写的是逻辑类型。除明确构造为 nullable int64 的列外，实际 Arrow 类型还受本批数据影响：例如所有值都为空的 `evidence_mode` 可能显示为 Arrow `null` 类型，读取程序应允许空值。

| 列                    | 类型/取值                                           | 含义和作用                                                         |
| --------------------- | --------------------------------------------------- | ------------------------------------------------------------------ |
| `episode_index`       | 整数                                                | 在这份导出里的 episode 编号                                        |
| `frame_index`         | 整数                                                | 在这份导出 episode 内的帧号，从 0 起                               |
| `source_episode_uuid` | 字符串                                              | 沿导出链继承的源 episode 稳定身份                                  |
| `source_frame_index`  | 整数                                                | 该帧在原始源 episode 内的帧号                                      |
| `arm`                 | `left` / `right` / `global`                         | 标签针对谁；默认 schema 没有 global 字段行                         |
| `field_id`            | 字符串                                              | 对应 schema 的字段机器标识                                         |
| `value_id`            | nullable int64                                      | 当前类别的稳定 ID；`null` 表示没有当前有效类别值                   |
| `applicability`       | `applicable` / `not_applicable` / `undetermined`    | 当前规则明确适用、明确不适用、还是无法确定                         |
| `annotation_status`   | `labeled` / `missing`                               | 是否存在当前类别值，不能代替审核状态                               |
| `review_status`       | `draft` / `reviewed` / `needs_review`               | 草稿、已审核、需要重新复核                                         |
| `evidence_mode`       | `state` / `behavior` / null                         | 保存/审核时使用的证据模式；未保存过的字段可为空                    |
| `label_source`        | `human` / `rule_suggestion` / `test_fixture` / null | 人工、规则候选、明确合成测试数据等来源；不等于审核结论             |
| `schema_version`      | nullable int64                                      | 该标签最后保存/审核对应的 schema 版本；不是无条件填当前版本        |
| `revision`            | nullable int64                                      | 该记录的工作项目修订号，辅助追溯；不是帧号、时间戳或跨项目唯一编号 |
| `future_seen`         | 布尔或 null                                         | 保存/审核时已登记该源 episode 进入过行为复核；见下文限制           |
| `effective_loss_mask` | 整数 0 / 1                                          | 这份片段内，这个字段是否贡献分类监督                               |
| `provenance`          | JSON 字符串                                         | 记录证据配置、候选来源、审核范围等附加信息；读取后还需 JSON 解析   |

当前逐帧导出列**不包含** `required`、`reason`、`retired_value_id`。这些是规则解析/界面可以给出的辅助信息；需要时根据 schema 和原始记录重算，不能假定磁盘表里也有同名列。删除类别的原始旧值要到 intervals 和历史 schema 中追溯。

### 8.3 几种容易混淆的情况

| 情况               | 例子                                   | `value_id`         | 意思                               | 审核有效且是中心时，mask 能否为 1 |
| ------------------ | -------------------------------------- | ------------------ | ---------------------------------- | --------------------------------- |
| 已明确回答普通类别 | close=not_ready                        | 0                  | “有证据表明现在条件不具备”         | 可以                              |
| 已明确回答 unknown | close=unknown                          | 默认 2             | “已经看了允许证据，仍判断不了”     | 适用时可以                        |
| missing            | close 没标                             | null               | “当前没有这个答案”                 | 不可以                            |
| not_applicable     | transport 的 close                     | 可空，也可保留旧值 | “这个阶段不应该问是否闭合就绪”     | 不可以                            |
| undetermined       | phase 没填/unknown，close 是否适用不明 | 可空，也可保留旧值 | “连现在该不该问这个问题都确定不了” | 不可以                            |

`unknown` 只在**字段适用**时作为这个字段的真实类别训练。父阶段 unknown 导致子字段 undetermined 时，即使子字段存着一个 unknown 值，也不会因此得到监督。

`null` 不等于 ID=0。比如 phase=0 是 idle，close=0 是 not_ready，adviser.x=0 是 none。把 null 补成 0 会凭空制造大量错误标签。适配器把 null 转成训练忽略值 `-100`，同时给 mask=0。

### 8.4 loss mask 的生成条件

当前规则引擎逐字段计算：

```text
effective_loss_mask = 1，当且仅当：
    该帧是当前片段中明确选中的训练中心
AND 当前字段 applicability == applicable
AND 当前字段 annotation_status == labeled
AND 当前字段 review_status == reviewed
AND 标签 schema_version == 当前 schema.version
```

大白话解释：**选了这道题、这道题适合问、答案已填、答案已审、审核用的还是这版规则，五项齐全才计分。**

这里没有“整帧必须所有字段都完成”的条件。只审核好了 phase，它就可以训练；adviser 缺失只让 adviser 自己不训练。历史或审核尾部即使保存着已审标签，这份副本 mask 也始终为 0。

审核入口会拦截/跳过内置语义冲突，例如 release ready 没有 place_align/holding；门控父值改变会让相关子标签需要复核。不过 mask 本身不是对画面真值、标定质量或全局语义正确性的自动证明。

尤其注意，mask 公式**不额外要求**动作区间 approved、`future_seen=false`、`label_source=human`、单位/坐标已验证或标注者身份齐全。那些是其他用途的条件，需要训练/数据审核流程另行检查。

### 8.5 provenance 和 future_seen 怎么读

`provenance` 是扩展记录，按来源出现不同键，并非每条都有相同结构。

| 常见键                           | 何时出现                | 含义                                                         |
| -------------------------------- | ----------------------- | ------------------------------------------------------------ |
| `history_config`                 | 状态模式保存和审核      | 当时允许的 H/T、采样方式、偏移和是否含当前                   |
| `review_scope`                   | 整段标签审核            | 本次人工确认的源帧范围 `start/end` 及 `mode`                 |
| `status`、`values`               | 接受自动 adviser 候选后 | 候选返回状态和各分量建议；不能替代外层 review_status         |
| `start`、`end`、`duration`       | 自动 adviser 候选       | 候选生成时所在输入数据集的窗口帧坐标、半开末端和实际持续秒数 |
| `needs_review`                   | 自动 adviser 候选       | 是否检测到需人工处理的往返歧义等；false 也仍是候选           |
| `rule_version`                   | 规则候选                | 生成候选使用的规则版本                                       |
| `coordinate_config`              | 自动 adviser 候选       | 当时的坐标、单位、变换、噪声及实测末端字段配置               |
| `test_fixture`、`description` 等 | 某些测试/自定义记录     | 测试或调用方附加说明，不能当作真实人工标签                   |

`coordinate_config` 中当前常见键如下：

| 键               | 含义                                                                                 |
| ---------------- | ------------------------------------------------------------------------------------ |
| `verified`       | 使用者是否已经确认原始单位与变换；不是程序自行测得的验证结论                         |
| `unit`           | 当前自动方向候选要求原始位置已为 `m`                                                 |
| `frame`          | 当前要求规范目标系为 `robot_base`                                                    |
| `transform`      | 从来源位姿坐标到规范基座系的 4×4 刚体变换；左上 3×3 表示旋转，最后一列前三项表示平移 |
| `position_noise` | 配置的静止位置噪声尺度，单位米；平移显著性阈值为 `max(0.005m, 3×噪声)`               |
| `angle_noise`    | 配置的静止角噪声尺度，单位弧度；角度显著性阈值为 `max(5°, 3×噪声)`，内部统一弧度计算 |
| `feature`        | 选用的实测末端字段，如 `observation.ee_pose_left`                                    |

坐标变换的旋转部分改变方向，平移部分在首末位移相减时抵消。噪声参数由使用者提供，当前工具不会自动估计一份可信静止噪声标定。

provenance 内的窗口不是自动重写的当前导出坐标：再次裁剪后不能直接拿其中的 frame 数字索引当前视频。外层源 UUID/源帧和 `source_map` 才是稳定追溯依据，必要时还需保存原工作项目。

`future_seen` 采用源 episode 级登记：进入行为模式时设置，后续保存/审核把该标记写到记录中。它不是逐字段、逐曝光的完整查看日志，也不是精确的未来窗口长度。

因此 `true` 不代表该状态标签一定泄漏；状态标签仍可以由允许历史独立支持。`false` 或 null 也不证明标注者从未在别处看过未来。工具的证据隔离帮助规范操作，不能消除人的记忆。

## 9. samples.parquet：样本资格、角色与采样

### 9.1 一行是什么，全部列是什么意思

每个导出数据帧对应一行，包括中心、前史和尾部，主键是 `(episode_index, frame_index)`。

| 列                    | 类型/取值            | 意义                                                                     |
| --------------------- | -------------------- | ------------------------------------------------------------------------ |
| `episode_index`       | 整数                 | 当前导出 episode 编号                                                    |
| `frame_index`         | 整数                 | 当前导出帧号                                                             |
| `center_is_selected`  | 布尔                 | 这一帧是否明确作为训练决策中心；DSEDataset 只把 true 的行列为样本        |
| `is_history_context`  | 布尔                 | 是否处于本片段某个后续中心可用的保留历史范围，不代表一定被稀疏采样命中   |
| `is_review_context`   | 布尔                 | 是否位于最后一个中心之后、仅供未来复核的尾部                             |
| `source_episode_uuid` | 字符串               | 源 episode 稳定身份                                                      |
| `source_frame_index`  | 整数                 | 原始源帧号                                                               |
| `split_group`         | 字符串               | 防止同源片段跨 train/validation/test 的分组身份；不是已经分好的 split 名 |
| `event_group`         | 字符串               | 为采样均衡构建的事件/阶段组标识；不是模型的事件预测目标                  |
| `pool`                | `key` / `background` | 关键采样池或普通采样池                                                   |
| `valid_fields`        | 整数                 | 这一帧所有臂/字段的 `effective_loss_mask` 之和；是有效字段数，不是类别数 |
| `sampling_weight`     | 浮点数               | 加权抽样使用的相对权重，不是字段 loss mask 或动作质量分                  |
| `boundary`            | 布尔                 | 是否在中心首帧或末帧附近约 1 帧范围内，包括紧邻上下文；不是额外标签      |
| `key_zone_left`       | 0 / 1 / null         | 左臂是否由 phase 派生为精细对准区域                                      |
| `key_zone_right`      | 0 / 1 / null         | 右臂同上                                                                 |

这几个角色标记**不是互斥的三选一**。一个中心帧也可能给后面的中心提供历史，因此 `center_is_selected=true` 与 `is_history_context=true` 可以同时出现。决定它是否作为独立样本的字段是 `center_is_selected`。

### 9.2 key_zone、pool 和 event_group 的区别

当前默认语义下：

- `key_zone_*`：phase 为 2 或 5 时为 1；其他明确阶段为 0；phase 缺失或为 8 时为 null。它是从阶段派生的门控信息，不是额外人工真值或独立预测头。
- `pool=key`：任一臂 phase 属于 `[2,3,5,7]`，或者接近 confirmed 事件；因此它比 key_zone 更宽，抓持检查和恢复也会进入关键采样池。
- `event_group`：附近有 confirmed 事件时使用最近事件的源帧构成组名，否则使用两臂当前 phase 值构成组名。邻近判断为约 ±0.25 秒对应的帧数。

这些是当前导出器的具体策略，其中阶段集合和 key_zone 的默认 unknown ID 使用内置约定。仅在 schema 编辑器增加新阶段，不会自动扩展采样策略或内置语义校验；更改核心阶段协议时须同时核对代码和实验配置。

事件组的字符串是内部统计/采样标识，不能当作稳定语义类别；key_zone/pool 的派生也不代表它们已经人工审核。

### 9.3 sampling_weight 怎么来，怎么用

只有**中心且 valid_fields>0** 的记录得到候选采样资格；仅上下文、全无有效监督的中心权重均为 0。

默认把概率质量分给 key 池 70%、background 池 30%，然后在各池中按来源组、事件/阶段组、组内唯一源帧和副本分摊，避免长轨迹或重复副本天然占多数。某一池无可用记录时，报告 warning，另一池按实际可用情况回退。

这里 70%/30% 是**抽样时的目标比例**，不会删除 70% 以外的数据，也不保证每一个有限 batch 都精确 70/30；普通 DataLoader 随机遍历不会自动执行这些权重。`DSEDataset.sample_indices` 使用有放回加权抽样；全无非零权重时明确报错。

采样权重不改变每字段是否有效，不应直接替代 loss mask，也不必再机械地乘进损失。训练集划分后，应在训练子集内重新检查池比例和组均衡；按全导出计算的权重，在过滤部分来源后不保证仍是同一比例。

## 10. source_map.parquet：来源与媒体对应

### 10.1 为什么要同时保存当前、parent、source

假设原始数据 A 裁剪成 B，又从 B 裁剪成 C：

```text
A：最初源数据      →      B：第一次导出      →      C：当前导出
source_*                 parent_*                 当前 episode/frame/index
```

当前坐标告诉你“在 C 里打开哪里”；parent 告诉你“这次直接从 B 的哪里取来”；source 告诉你“最初在 A 的哪里”。首次导出时 parent 与 source 帧号通常相同，再次裁剪后通常不同。

### 10.2 全部列

每个当前导出帧一行，主键也是 `(episode_index, frame_index)`。

| 列                           | 含义                                          |
| ---------------------------- | --------------------------------------------- |
| `episode_index`              | 当前导出 episode 编号                         |
| `frame_index`                | 当前导出 episode 内帧号                       |
| `index`                      | 当前导出跨所有 episode 的全局行号             |
| `timestamp`                  | 当前导出 episode 内时间，首帧重置为 0，单位秒 |
| `source_episode_uuid`        | 原始源 episode 稳定身份，沿本工具导出链继承   |
| `source_frame_index`         | 原始源 episode 内帧号                         |
| `source_episode_index`       | 原始源数据集的 episode 整数编号               |
| `source_dataset_fingerprint` | 最初来源数据集的内容指纹                      |
| `source_timestamp`           | 原始源帧时间，单位秒                          |
| `source_index`               | 原始源数据集的全局行号                        |
| `parent_episode_index`       | 本次直接输入数据集的 episode 编号             |
| `parent_frame_index`         | 本次直接输入 episode 内帧号                   |
| `parent_timestamp`           | 本次直接输入帧的时间，单位秒                  |
| `split_group`                | 继承的同源划分组                              |
| `media_mapping`              | JSON 字符串，各相机的原始视频帧对应关系       |

`media_mapping` 解析后形如：

```json
{
  "observation.images.cam_high": {
    "source_ordinal": 40,
    "source_pts": 1.333333
  }
}
```

实际样例包含三相机。

| 媒体键           | 含义                                                                  |
| ---------------- | --------------------------------------------------------------------- |
| `source_ordinal` | 来源视频按展示时间排列的帧序号，从 0 起；不必假定永远与数据行帧号相等 |
| `source_pts`     | 来源视频该帧的展示时间，当前保存为**秒**，不是编码器原始整数 tick     |

再次导出会优先保留已有祖先媒体映射，不能拿这个 source ordinal 直接当作当前 MP4 的帧号。

### 10.3 稳定身份的实际边界

首次导入原始数据时，用数据集相对路径和文件内容计算 SHA-256 指纹，再由“指纹 + episode 编号”确定 UUID；默认 split_group 就是该源 episode UUID。单纯搬动完整目录不会改变内容身份，沿导出链继续继承源键。

但这不是自动的“物理采集身份识别”：同一采集另存成另一种格式、改了文件内容，或者由别的工具重新编码，不能保证自动识别成同源；不同 episode 若来自同一采集 session，也不会自动合成更大的 session 组。正式划分时仍要补充采集级来源管理。

## 11. intervals.parquet：区间、单帧修正、动作审核与事件

### 11.1 外层只有两列

| 列        | 含义                                                              |
| --------- | ----------------------------------------------------------------- |
| `table`   | 内部记录种类：`annotations` / `selections` / `reviews` / `events` |
| `payload` | 该条记录的 JSON 字符串，内部字段随 table 不同                     |

读一行后，先看 table，再 `json.loads(payload)`。某些内部字段本身又是 JSON 字符串，如 `provenance`、`details`，需要再解析一次。

这个文件保存的是导出时相关工作表的**当前记录快照**，不是完整编辑日志。对带入的源 UUID，当前实现会携带该源的区间/审核/事件记录，**不保证仅含当前裁剪范围内的记录**。因此附件可能描述导出里没有实际视频的源帧；它保留的是标注/审核记录，不会因此把那部分媒体也带上。

### 11.2 table=annotations 的 payload

| 键             | 含义                                                         |
| -------------- | ------------------------------------------------------------ |
| `id`           | 导出前 SQLite 内部记录号，不是跨项目稳定主键                 |
| `source`       | 源 episode UUID，对应其他表的 source_episode_uuid            |
| `start`、`end` | 原始源帧的半开范围 `[start,end)`                             |
| `arm`          | left / right / global                                        |
| `field`        | 对应 labels.field_id                                         |
| `value`        | 原始保存的稳定类别 ID 或 null；删除类别后仍可在这里追溯旧 ID |
| `kind`         | `range` 区间赋值，或 `point` 单帧例外；point 范围长度为 1    |
| `status`       | 对应标签的 draft / reviewed / needs_review                   |
| `mode`         | state / behavior                                             |
| `label_source` | human / rule_suggestion / test_fixture 等                    |
| `future_seen`  | 保存时的登记值；此原始表通常为 SQLite 的 0/1 整数            |
| `version`      | 对应 labels.schema_version                                   |
| `revision`     | 对应记录修订号                                               |
| `provenance`   | JSON 字符串，含当时证据/候选等信息                           |

默认单帧例外优先于区间，**显式单帧 missing 也会覆盖区间值**。界面可选择统一覆盖来移除指定字段、适用范围内的单帧例外；导出保存的是最终记录状态，不额外保存一个永久的 `point_policy` 列。

逐帧 labels 是按这些记录和当前 schema 计算后的结果。训练分类通常直接使用 labels，不应把 interval 里的旧类别绕过当前规则当作有效训练答案。

### 11.3 table=selections 的 payload

| 键             | 含义                              |
| -------------- | --------------------------------- |
| `id`           | 工作表内部记录号                  |
| `dataset`      | **本次输入数据集**的指纹          |
| `episode`      | 本次输入数据集的 episode 编号     |
| `start`、`end` | 本次输入 episode 坐标里的中心区间 |

这里的 start/end 是直接输入坐标，与 annotations/reviews 的原始源帧坐标可能不同。重新导入时，工具会根据 samples 中当前导出的中心标记恢复新数据集选区，不能把这些旧 selections 数字直接套用到新 episode。

### 11.4 table=reviews 的 payload：动作质量审核

| 键             | 含义                                                   |
| -------------- | ------------------------------------------------------ |
| `id`           | 内部记录号                                             |
| `source`       | 源 episode UUID                                        |
| `start`、`end` | 原始源帧半开范围                                       |
| `status`       | approved / rejected / unreviewed                       |
| `reason`       | 人工填写的原因，如错误闭合、恢复示教等；当前是文本备注 |

大白话解释：**这张审核单问的是“示教动作适不适合当模仿对象”，而 labels.review_status 问的是“这个语义答案有没有审过”。** 二者不能互相代替。

没有 reviews 记录的范围不能默认为 approved。标了 rejected 也不会删除原始 action、改写视频或自动让 DSE 状态标签失效：失败画面仍然能教 DSE 识别 not_ready、recover 等。当前适配器不生成 BC 动作块资格 mask，VLA 训练需要自行消费这里的审核记录。

### 11.5 table=events 的 payload

| 键        | 含义                                                         |
| --------- | ------------------------------------------------------------ |
| `id`      | 内部记录号                                                   |
| `source`  | 源 episode UUID                                              |
| `frame`   | 原始源帧号                                                   |
| `arm`     | 事件针对的手臂                                               |
| `type`    | 事件类型；规则候选常为 `open` / `closed`，手动类型见实际记录 |
| `status`  | 常见 suggestion / confirmed；确认前不是已核实事件            |
| `details` | JSON 字符串，保存来源和候选生成配置                          |

手动事件的 details 常为 `{"source":"human"}`。规则事件的 details 可能包含：

| 键                                                | 含义                                                      |
| ------------------------------------------------- | --------------------------------------------------------- |
| `feature`                                         | 使用 `observation.state` 实测通道，还是 `action` 命令通道 |
| `dimension`                                       | 该向量的通道下标；需结合 info.features 的 names 解释      |
| `rule_version`                                    | 当前滞回事件规则为 `hysteresis-1`                         |
| `calibration.verified`                            | 使用者是否确认过单位、方向和阈值配置                      |
| `calibration.unit`                                | 通道单位说明                                              |
| `calibration.closed_threshold` / `open_threshold` | 两个不同开闭阈值                                          |
| `calibration.closed_below`                        | 较小数值是否表示闭合                                      |
| `calibration.min_duration`                        | 新状态须持续的最短秒数，减少噪声抖动                      |

“滞回”就是开与关用不同阈值，避免读数在一个临界值两边抖动，反复产生事件。命令通道生成的“闭合”不能自动视作实测已闭合，更不能直接当 holding 或 ready。

confirmed 事件用于关键采样池及事件分组；当前自动 adviser 在事件边界截断时会读取该来源的已保存事件，未确认候选也可能影响截断。应清理/复核候选，不能假定所有用途都只看 confirmed。

## 12. manifest.json：这次导出的交付清单

### 12.1 全部顶层键

| 键                            | 含义与使用方式                                                                           |
| ----------------------------- | ---------------------------------------------------------------------------------------- |
| `tool_version`                | 导出工具声明版本，当前为 0.1.0；细节仍应结合代码版本和清单内容，不能只凭此值推断所有功能 |
| `format`                      | 当前格式 `LeRobot-v2.1+DSE-1`                                                            |
| `schema_version`              | 当前活动规则版本                                                                         |
| `schema_hash`                 | 当前 schema 的规范化内容 SHA-256                                                         |
| `source_fingerprint`          | **本次直接输入数据集**的指纹；再次导出时可能是上一次导出目录的指纹                       |
| `source_episode_uuids`        | 实际带入帧所属的源 episode UUID 列表                                                     |
| `source_dataset_fingerprints` | 源映射中继承的原始来源数据集指纹列表，与直接输入指纹不一定相同                           |
| `context_seconds`             | 连续前史保留容量与审核尾部参数                                                           |
| `history_sampling`            | 这份导出默认的历史取样配置                                                               |
| `selections`                  | 本次输入数据集坐标下的训练中心选区列表，含 id/dataset/episode/start/end                  |
| `sampling`                    | 采样池比例和组均衡策略声明                                                               |
| `encoding`                    | 视频重编码参数                                                                           |
| `checksums`                   | `相对文件路径 → SHA-256` 的校验字典                                                      |
| `source_roots_required`       | false 表示读取这份导出无需保留原始目录路径；不意味着缺失历史可恢复或标定已验证           |

### 12.2 嵌套配置

| 路径                                | 含义                                                                 |
| ----------------------------------- | -------------------------------------------------------------------- |
| `context_seconds.history`           | 连续前史容量 C，单位秒，不等于所有中心实际都有这么长历史             |
| `context_seconds.review`            | 审核尾部参数，当前 0.25 秒；轨迹末端可能不足                         |
| `history_sampling.horizon_seconds`  | 默认模型历史跨度 H                                                   |
| `history_sampling.num_frames`       | 每相机总时刻数 T，含当前                                             |
| `history_sampling.offsets_seconds`  | 从最早到当前的“向过去偏移量”，如 `[0.6,0.4,0.2,0]`；这里过去量写正数 |
| `history_sampling.sampling`         | 当前为 `at_or_before`                                                |
| `history_sampling.includes_current` | 当前为 true                                                          |
| `sampling.key_ratio`                | key 池期望采样质量，如 0.7                                           |
| `sampling.group_first`              | true 表示导出权重按组均衡；不是训练器自动分组的开关                  |
| `encoding.codec`                    | 当前编码器 libx264，输出 H.264                                       |
| `encoding.crf`                      | 当前为 18，编码质量参数；不表示无损                                  |
| `encoding.preset`                   | 当前 fast，编码速度/压缩权衡参数                                     |
| `encoding.pix_fmt`                  | 当前 yuv420p                                                         |

manifest 的偏移量是向过去的正数；适配器的 `history_target_offsets` 是相对当前的负数。二者符号不同，含义一致。

### 12.3 校验和能证明什么

导出时为已生成的标准数据、视频和其他附件记录文件 SHA-256；**manifest 本身不在自己的 checksums 中**，否则形成自引用。schema_hash 计算的是 schema 对象的规范化内容，checksums 中 schema.json 的哈希计算的是文件字节，两者不必相等。

重新导入和导出检查器会核对清单文件；`DSEDataset` 当前默认核对 annotations 范围的校验和，不会在初始化时完成所有大视频的全文件哈希检查。需要完整媒体完整性验证时，可调用 `verify_manifest(root)` 或打开导出检查器。

校验和用于检测缺失或改变，不能证明人工标签本身正确，也不是带签名的身份认证。不要直接手改已发布 Parquet/JSON 后当成同一份快照使用；应通过工作项目修改并导出到新目录。

## 13. validation_report.json：如何读导出报告

| 键                | 实际计算含义                                                                  |
| ----------------- | ----------------------------------------------------------------------------- |
| `center_count`    | 选中中心记录数，按当前导出副本计数                                            |
| `context_count`   | 非中心记录数；通常 `center_count + context_count == total_frames`             |
| `complete`        | 至少一个有效字段，且没有“required 明确为 true 但 mask=0”的中心数              |
| `partial`         | 至少一个有效字段，但仍有上述必填缺口的中心数                                  |
| `no_supervision`  | 所有字段 mask 都为 0 的中心数                                                 |
| `missing_fields`  | 中心上 required 明确为 true、但 mask=0 的字段×帧总数；不只指 value_id=null    |
| `counts`          | 中心各臂各字段的 value_id 计数，键形如 `left.phase:8` 或 `left.phase:missing` |
| `warnings`        | 如某个采样池无可用数据等提示                                                  |
| `segments`        | 每个片段的输入 episode、中心范围、实际保留范围和新 episode 编号               |
| `elapsed_seconds` | 写报告时已用秒数；之后还有最终媒体验证，不是作业完整总耗时的严格替代          |

segments 的各键：

| 键               | 含义                                                                      |
| ---------------- | ------------------------------------------------------------------------- |
| `source_episode` | 本次输入数据集中的 episode 编号；再次导出时指直接父集，不一定是最初源编号 |
| `center`         | 输入坐标下 `[start,end)` 中心范围                                         |
| `retained`       | 输入坐标下实际保留的 `[low,high)`，含上下文                               |
| `new_episode`    | 对应当前导出 episode 编号                                                 |

解释报告时注意四点：

1. `complete` 是上述计数条件下的完成，不是语义准确率 100%、所有头都有答案、所有依赖都已确定或动作质量已批准。例如 phase=unknown 时某些子字段 required 为未知，不算明确必填缺口。
2. `missing_fields` 还可能来自有值但未审、旧版本等，不能简单理解为“多少空格没填”。
3. `counts` 包含当前中心保存/解析出的类别，不按 mask=1 过滤，也不是分组去重后的类频率。计算训练 class weight 时，应另按有效监督和训练来源去重统计。
4. 报告不声称生成了一份详尽的人类语义/BC 质量审计。导出成功也不保证一定有可训练标签；全无监督的数据仍可用于核对裁剪和媒体。

## 14. 标准 LeRobot 文件发生了哪些变化

新增附件之外，工具还会生成新的标准部分。它不是把原始目录原封不动复制一份。

### 14.1 数据文件：`data/chunk-*/episode_*.parquet`

选定保留范围内，原 observation/action 数值和其物理存储精度保留；episode/frame/global index、task_index 和时间按新数据集重新编排。默认样例常见列如下：

| 列                                   | 意义                                      | 导出处理及训练注意                                                            |
| ------------------------------------ | ----------------------------------------- | ----------------------------------------------------------------------------- |
| `observation.state`                  | 18 维实测状态，含两臂、夹爪与头部关节通道 | 保留数值；通道含义读取 info.features 的 names，不默认为其他机器人的 16 维布局 |
| `action`                             | 18 维示教动作/命令向量                    | 保留原值，不因 rejected 或 readiness 自动改成正确动作；DSE 输入不读它         |
| `observation.ee_pose_left/right`     | 每臂 7 维实测末端位姿                     | 默认样例为 x/y/z/qx/qy/qz/qw；坐标系、单位需核实                              |
| `observation.ee_pose_cmd_left/right` | 每臂 7 维命令末端位姿                     | 命令不等于实测，DSE 输入不读它                                                |
| `frame_index`                        | 新 episode 内帧号                         | 从 0 开始                                                                     |
| `timestamp`                          | 新 episode 内时间，秒                     | 原时间减本片段第一条保留行时间，不是减第一条中心时间                          |
| `episode_index`                      | 新 episode 编号                           | 从 0 连续编排                                                                 |
| `index`                              | 新数据集全局行号                          | 跨 episode 连续编排                                                           |
| `task_index`                         | 对应 tasks.jsonl                          | 可能重新映射，不能沿用原数据集 task_index 查新任务表                          |

本地原始样例的 info 曾把部分字段声明为 float32，但 Parquet 实际是 double/float64。导出按实际类型保留，并修正 features 声明；这不是偷偷降低精度或做了数值归一化。

视频像素保存在 MP4，不是把三相机像素数组加进这些数据行。字段实际有哪些，以这份数据集的 features 和 Parquet schema 为准。

### 14.2 视频文件：`videos/chunk-*/*/episode_*.mp4`

工具解码来源视频、按映射精确选择帧，再重编码为 H.264/yuv420p，保持源分辨率和标称 FPS，重新生成视频时间。当前样例的 640×480 导出视频并不会变成训练读取器的 256×256。

H.264/CRF18 是有损重编码：保留对应场景和帧关系，不承诺和原 AV1 的字节或 RGB 像素完全相同。同一源帧在两个独立片段中的编码副本也可能有像素差异，应通过 source_key 判断同源，不用像素完全相等判断身份。

数据行取历史是因果的，不代表物理相机曝光同步已经被证明：当前媒体层按约半帧容差匹配最近视频 PTS，仍需独立核实真实采集时钟、曝光/遥测同步与陈旧输入。这是数据质量验收的一部分。

### 14.3 meta/info.json

### 14.4 tasks.jsonl、episodes.jsonl

| 文件             | 每行键                             | 意义                                                |
| ---------------- | ---------------------------------- | --------------------------------------------------- |
| `tasks.jsonl`    | `task_index`、`task`               | 任务编号和文本；例如 `Put the banana on the plate.` |
| `episodes.jsonl` | `episode_index`、`length`、`tasks` | 新 episode 编号、实际保留帧数、其中任务文本列表     |

tasks 中的原任务文本会保留。**当前界面“任务与几何参考”填写的目标抓取部位、承接区域、W 和标定说明，保存在工作项目偏好中，导出器不会自动把它们写入 tasks.jsonl 或另建完整任务协议文件。** 接收训练数据时，应另外交付经版本管理的任务/标定协议，不能以为目录已包含全部口头约定。

自动事件的配置可在 details 中找到，接受的 adviser 候选可在 provenance 中找到坐标配置；这不等于所有手动标签都自动携带完整任务协议。

### 14.5 episodes_stats.jsonl、stats.json

`episodes_stats.jsonl` 每行有 `episode_index` 和该片段 `stats`；`stats.json` 是整个导出数据的汇总。各特征统计常见键为：

| 键            | 含义                                                                   |
| ------------- | ---------------------------------------------------------------------- |
| `min` / `max` | 每维最小/最大值                                                        |
| `mean`        | 每维均值                                                               |
| `std`         | 当前实现使用总体标准差（NumPy 默认 ddof=0）                            |
| `count`       | 形如 `[N]` 的参与帧/行数；视频统计数值基于各通道像素，count 仍记录帧数 |

数值向量的统计按维度保存；视频 min/max/mean/std 按 RGB 通道保存，常见形状为 `[3,1,1]`，像素值范围按 `[0,1]` 计算，且统计的是**实际发布后的重编码视频**。

统计包括导出的全部保留行和副本，不按中心、有效监督或未来 train/validation/test 自动过滤。它用于描述和标准格式兼容，**不能直接当作严格训练集归一化统计**。类别 ID 和 mask 也不应该做均值方差归一化。

## 15. 下游 DSE 实际读取到什么

### 15.1 原生 LeRobot 与 DSE 适配器的分工

原生 LeRobot 读取标准 `meta/data/videos`，不会自动连接附件、应用 DSE loss mask、生成动态分类头或过滤 rejected 动作。项目曾用锁定的官方 `lerobot==0.3.3` 验证 v2.1 标准部分可独立读取；这不代表任意最新版训练器都会自动支持本项目附件。

项目提供 `dse_tool.adapter.DSEDataset`，专门连接附件与观测：

```python
from dse_tool.adapter import DSEDataset, encode_class_targets

reader = DSEDataset(
    "/path/to/export_dataset",
    cache="/path/to/separate-work/train-cache",  # 缓存放在数据集外
)
item = reader[0]
batch = reader.batch([0, 1])
encoded = encode_class_targets(batch["labels"], reader.schema)
```

示例前提是数据集至少有两个中心；不要求两个中心都有非零监督，训练端仍要看 mask。初始化检查 annotations 校验和及标签门控/mask 与当前共享规则的一致性。当前实现会将附件表读入内存，不应据此推断海量数据加载性能。

### 15.2 batch 的字段与形状

记 B 为 batch 大小、T 为历史总时刻数、S 为读取尺寸（默认 256）。当前适配器要求 3 相机，按 high、left、right 命名约定排序；换相机布局须显式核对，不能以为它会自动理解任意机器人。

| 键                       | 默认 batch 形状/类型         | 含义                                                                             |
| ------------------------ | ---------------------------- | -------------------------------------------------------------------------------- |
| `images`                 | `[B,T,3,3,S,S]`，float32     | 依次为 batch、时刻、相机、RGB 通道、高、宽；当前只 resize 和除 255，范围 `[0,1]` |
| `image_valid_mask`       | `[B,T,3]`，bool              | 对应时刻/相机是否有实际输入                                                      |
| `state`                  | `[B,T,18]`，当前实现 float64 | 按相同历史行取出的实测状态，尚未做模型标准化                                     |
| `state_valid_mask`       | `[B,T]`，bool                | 历史行是否存在                                                                   |
| `ee_pose_feedback`       | `[B,T,2,7]`，float64         | 左/右实测末端 x/y/z/qx/qy/qz/qw                                                  |
| `ee_pose_valid_mask`     | `[B,T,2]`，bool              | 对应臂/时刻的反馈字段是否存在；不是已标定或噪声合格证明                          |
| `history_frame_indices`  | `[B,T]`，int64               | 当前导出 episode 内实际取到的行号，缺失为 -1                                     |
| `history_target_offsets` | `[B,T]`，秒                  | 目标相对时间，如 `[-0.6,-0.4,-0.2,0]`                                            |
| `history_actual_offsets` | `[B,T]`，秒                  | 实际行相对当前时间，可比目标更早；缺失为 NaN                                     |
| `history_config`         | 配置字典                     | 该 reader 统一使用的 H/T 和采样约定                                              |
| `task`                   | 长度 B 的字符串列表          | 原任务文本，不自动追加界面几何说明                                               |
| `labels`                 | `arm → field_id → [B]`，整数 | 当前中心的稳定类别 ID；null 转为 -100                                            |
| `loss_masks`             | 同样嵌套的 `[B]`，整数       | 当前中心逐字段有效监督 mask                                                      |
| `source_keys`            | 长度 B 的字典列表            | 源 UUID、源帧、split_group 和当前 schema 版本，供分组/追溯，不能当网络输入       |
| `coordinates_verified`   | false                        | reader 没有把所有原始反馈认定为已验证规范坐标                                    |

这些是**加载时生成的 batch 字段**，不是说导出目录里还多了一个 `images.npy`、一个 36D Parquet 或这些同名文件。

适配器不返回 action、末端命令或未来图像；标签只对应当前决策帧，不把每个历史时刻都当作当前标签的额外训练目标。

### 15.3 三种 mask 分别处理什么

| 对象                     | 回答的问题                         | 谁必须执行                     |
| ------------------------ | ---------------------------------- | ------------------------------ |
| 输入存在性 mask          | “这一时刻/视角/末端反馈真的存在吗” | 模型编码、attention 和池化     |
| 标签 loss mask           | “这个字段的答案现在可以用来判分吗” | DSE 损失函数                   |
| 动作质量审核及动作块资格 | “这段动作能作为模仿目标吗”         | 后续 VLA/BC 样本构建与训练逻辑 |

返回 mask 不等于已经执行 mask。只把缺失输入置零，网络仍可能把这些零当成真实状态；只保存 `effective_loss_mask`，普通交叉熵仍可能把无效答案算进损失。

当前输入 mask 主要表示行/字段是否存在；解码或映射失败通常报错，不是自动产出一个“质量较差”的 mask。末端四元数、单位、时钟质量需要独立检查。

### 15.4 36D 本体接口是什么

`proprioception36` 可把每个时刻的 18D state 与双臂末端反馈组合为：

```text
18D state + 左臂(位置3D + 旋转6D) + 右臂(位置3D + 旋转6D) = 36D
```

旋转 6D 取规范旋转矩阵的前两列，不是再增加 6 个关节。配置必须明确 `verified=true`、`unit="m"`、`frame="robot_base"` 和经核实的 4×4 刚体变换；它不会自动发现原始单位或进行单位换算。

先筛选真实有效的 state/末端时刻再转换，不能把 padding 的全零四元数传入。函数会拒绝无效四元数。转换和标准化后的特征是训练侧产生的，不是工具已将原始 18D 数据改写成 36D。

## 16. 训练时必须明确处理的事项

### 16.1 先按来源分组，再分训练/验证/测试

最少按 `split_group` 划分，确保同一源 episode 的中心、上下文副本和再导出片段全部在同一个集合。正式采集还应考虑 session、场景、对象等更高层组。

不能按新 episode 随机分，更不能把相邻中心帧随机打散后称作独立测试：同一原录像的重叠画面和动作可能同时出现，指标会被抬高。`meta/info.json` 中全是 train 的字符串只是导出标准布局，不能代替研究划分。

`reader.sample_indices` 默认面对 reader 的全部中心，**不接受 split 过滤参数**。如果一个导出目录同时含未来 train 和 test，先建立训练子集，再在子集内抽样。最小写法如下：

```python
import random

train_groups = {"<已划入训练的 split_group>"}
train_indices = [
    i for i, row in enumerate(reader.centers)
    if row["split_group"] in train_groups and row["sampling_weight"] > 0
]
if not train_indices:
    raise ValueError("训练来源内没有可抽样的有效中心")
indices = random.Random(0).choices(
    train_indices,
    weights=[reader.centers[i]["sampling_weight"] for i in train_indices],
    k=16,
)
batch = reader.batch(indices)
```

这段只演示隔离来源后相对权重抽样；若要严格实现训练子集自己的 70/30 和来源组均衡，须在子集内重新计算采样分布。验证/测试通常按明确规则遍历与报告，不沿用有放回训练采样来估计总体指标。

### 16.2 分类 ID、缺失值和 masked loss

先用 `encode_class_targets` 把稳定 ID 转为 logits 下标，再只在 `loss_masks==1` 的位置计算交叉熵。不能把类别 ID 当回归目标，不能把 unknown 并入负类，也不能先用 -100 去索引类别权重再乘 0。

若训练环境有 PyTorch，一个单头损失的最小示意是：

```python
import torch
import torch.nn.functional as F

def masked_head_loss(logits, encoded_targets, loss_mask):
    # encoded_targets 已经由稳定 ID 映射为当前 head 的连续下标。
    targets = torch.as_tensor(encoded_targets, device=logits.device, dtype=torch.long)
    valid = torch.as_tensor(loss_mask, device=logits.device).bool() & (targets != -100)
    if not valid.any():
        return logits.sum() * 0.0  # 保留计算图，不对空集合求均值。
    return F.cross_entropy(logits[valid], targets[valid])
```

这是训练端实现示意，不是当前工具已包含完整损失/网络。各头应按自身有效数归一化；一个头无监督返回 0，其他头仍可训练。训练损失使用**真值/schema 的适用性**，不能用模型自己预测的 phase 关掉它答错的子头。

### 16.3 图像预处理、浮点精度与归一化

当前 reader 图像只完成 RGB、resize 和 `[0,1]` 缩放，未执行目标视觉 checkpoint 的完整 processor 归一化。训练端要按模型要求做一致预处理，避免重复除 255 或训练/部署不同处理。

state/末端当前返回 float64，模型通常需要显式转换为目标浮点类型；转换不应混入类别和整数索引。18D 布局读取 names，不能凭夹爪在样例中的位置写死跨机器人映射。

`training_statistics(reader, train_groups)` 只统计指定训练来源里、按源 UUID+源帧去重的**中心帧 18D state**，返回 mean/std/count/split_groups：

```python
from dse_tool.adapter import training_statistics
stats = training_statistics(reader, train_groups)
```

它不按标签 mask 筛成“仅有监督的中心”，不统计完整历史输入分布或完整 36D，不生成图像 processor，也不自动标准化 batch。若训练使用不同统计口径，应显式实现并记录；零方差保护、末端派生量统计、模态选择与应用都由训练端完成。

### 16.4 改变历史或输入模态后，要复核证据是否仍够

reader 可以覆盖 manifest 的 H/T，但不能超过保留容量。每个 reader、每份导出统一一套默认 H/T，不支持单 batch 内逐样本随机 H/T 或变长 collate。

把 0.6 秒历史改成单当前帧，或者关掉实测本体，只保留图像，可能让原本可观察的 holding/recover 等真值变得无法判断。**当前 reader 不会因此自动清掉旧 reviewed 或 mask，也不自动重新审核标签。** 应检查 provenance，按新的证据配置复核，必要时建立独立实验标签版本。

缺失历史的实际偏移是 NaN，时间编码前须按存在性 mask 清零；不能把 NaN 直接喂给网络。T 要参与模型序列长度和 mask 构建，不能写死 4 时刻。不同目标可能落在同一真实数据行，按实际时间表示，不伪装成不同曝光。

### 16.5 状态真值与未来派生 adviser 不能泄漏进在线输入

phase/holding/readiness 是由当前及允许过去证据支持的状态；adviser 制作监督可以看未来。**用未来制作标签，不等于允许未来作为预测输入。**

DSE 前向不应包含 action、ee_pose_cmd、未来图、未来末端、人工 phase、event_group、split_group 或审核结论。这些信息可以制作目标、做划分或审计，不能成为在线模型的捷径。

未来派生 adviser 的真值也不能直接当作正式测试时“模型预测的提示”。后续给 VLA 做条件训练，应按既定分组/折外方案生成预测，区分预测提示与真值 oracle；当前工具没有自动完成这些训练与评估流程。

### 16.6 DSE 标签可用，不代表原动作可以做 BC

例如一帧明显偏位、close=not_ready，后续示教却错误闭合：这帧可用于训练 DSE 识别 not_ready，但原错误动作不应因为标签存在就变成正确模仿目标。

动作审核记录还必须由 BC 样本构建读取。若一个动作块覆盖 rejected 或未按协议批准的区域，首轮保守做法是整块不进入正向 BC；只删错误动作的起始帧不够。例如 80～129 帧的动作块覆盖第 100 帧错误闭合，起点 80 的样本也要处理。

当前导出只为 DSE 保留有限历史和 0.25 秒审核尾部，不保证提供 VLA 所需长动作块。短裁剪集不能自动替代完整动作训练数据；必要时通过源映射回读独立保存的完整原始来源，并核验整个目标块资格。

工具没有生成 `bc_action_mask`、`corrected_rollout_id`、专家纠偏轨迹或改好的 action。删除错误监督只能停止教错，不能凭空教会正确纠偏；后者需要真实、可追溯的正确目标。

### 16.7 复现实验还应保存什么

除完整数据集外，训练项目应保存实际 train/validation/test 来源组、代码版本、schema/hash、class_ids、H/T、模态开关、相机顺序、预处理、规范坐标配置、归一化统计、采样配置和任务协议。当前工具尚未实现具名 reviewer 与逐条审核时间字段，不能把 revision 当作审核员身份证明。

这些项中，部分已在导出附件，部分仍需单独管理；特别是界面偏好里的目标/承接区域/W/标定备注，没有完整独立导出协议文件。

正式训练还应排除明确的 `test_fixture` 和合成演示来源。测试夹具可以为了验证规则而具有 mask=1；mask 不负责判断数据是不是实际机器人采集。

## 17. 实际例子与自行检查方法

### 17.1 真实机器人导出：160 帧不等于 160 个训练样本

项目已有真实文件：[`exports/real-history-20261031-moved/`](../exports/real-history-20261031-moved/)。它用于验证读取、裁剪、搬移和历史配置，没有伪造人工语义标签。

| 项目            | 实际内容                                                        |
| --------------- | --------------------------------------------------------------- |
| 输入 episode    | 0                                                               |
| 选中中心        | 原输入帧 `[190,193)`，共 3 帧                                   |
| 历史配置        | H=5 秒、T=3                                                     |
| 实际保留        | 输入帧 `[40,200)`，共 160 帧                                    |
| 新 episode      | 0，本地帧 0～159                                                |
| 第一条中心      | 本地帧 150，对应原帧 190                                        |
| 第一条中心历史  | 原帧 40/115/190，即新本地帧 0/75/150                            |
| labels 行数     | 160×16=2560                                                     |
| DSEDataset 长度 | 3，按中心数计算                                                 |
| 有效监督        | 当前真实样例没有语义标签，三个中心全部 no_supervision，权重为 0 |

这说明标准媒体/数值裁剪成功与有了可训练的人工语义监督是两项验收。可以读取该导出的 batch 检查观测，但加权抽样会因全无监督明确报错。

### 17.2 合成重叠例子：同一答案在两份副本里 mask 不同

项目已有明确标为测试夹具的文件：[`workspaces/inspector-overlap-demo/synthetic-overlap-export/`](../workspaces/inspector-overlap-demo/synthetic-overlap-export/)。它不是机器人真实人工标签。

来源中心为 `[20,24)` 与 `[30,34)`；导出两个 episode，共 58 条保留行、8 个中心、39 个唯一源帧，包含 19 条额外副本。

| 当前记录       | 对应源帧 | 角色                         | left.phase | 审核     | mask |
| -------------- | -------: | ---------------------------- | ---------- | -------- | ---: |
| EP0 / 本地帧18 |       20 | 中心，同时可给后续中心作历史 | 8 unknown  | reviewed |    1 |
| EP1 / 本地帧8  |       20 | 仅前史                       | 8 unknown  | reviewed |    0 |
| EP1 / 本地帧0  |       12 | 仅前史                       | null       | draft    |    0 |

第三行虽然没有标签，实际 observation.state 仍为 `[12,13,…,29]`，不是零。**真实存在但没标的历史，与加载时根本不存在历史所产生的零 padding，不是一回事。**

### 17.3 不写代码也能检查

在界面打开“导出检查器”，选择完整导出目录后：

1. 看片段地图：中心、前史、审核尾部与同源重叠是否符合预期。
2. 选择具体帧：对照原始观测、nullable 标签、审核状态和 loss mask。
3. 查看来源映射：核对原始 UUID/帧/时间与当前坐标。
4. 选择中心的“训练输入预览”：核对实际抽到的 T 个时刻、三相机和缺失 mask。
5. 打开文件内容：查看真实 Parquet 列、分页记录及 JSON，不依赖当前工作项目里的未导出编辑。

检查器直接检查磁盘快照，只读数据集；缓存写在工作目录。细节见[导出检查器说明](EXPORT_INSPECTOR_2026-10-31.md)。

### 17.4 用 Python 查看磁盘上的真实文件

在安装本项目环境后，可运行下例。它只读导出文件：

```python
import json
from pathlib import Path
import pyarrow.parquet as pq

root = Path("/path/to/export_dataset")
manifest = json.loads((root / "annotations/manifest.json").read_text())
schema = json.loads((root / "annotations/schema.json").read_text())
samples = pq.read_table(root / "annotations/samples.parquet").to_pylist()
labels = pq.read_table(root / "annotations/labels.parquet").to_pylist()

centers = [r for r in samples if r["center_is_selected"]]
print("默认历史：", manifest.get("history_sampling"))
print("活动字段：", [f["field_id"] for f in schema["fields"]])
print("保留帧数 / 中心数：", len(samples), len(centers))
print("有效字段×帧数：", sum(r["effective_loss_mask"] for r in labels))

center = centers[0]
records = [
    r for r in labels
    if (r["episode_index"], r["frame_index"])
       == (center["episode_index"], center["frame_index"])
]
for r in records:
    print(r["arm"], r["field_id"], r["value_id"],
          r["applicability"], r["review_status"], r["effective_loss_mask"])

intervals = pq.read_table(root / "annotations/intervals.parquet").to_pylist()
for row in intervals:
    if row["table"] == "reviews":
        print("动作质量审核：", json.loads(row["payload"]))
```

大型数据可改为 Arrow 过滤/分页读取，以上是帮助理解的小数据示例。界面/reader 当前的全表内存策略尚无海量规模验收。

## 18. 常见误解、术语和实现依据

### 18.1 常见问题

| 问题                                                            | 正确理解                                                                                              |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 标完后原始目录多了 9 个文件吗？                                 | 原始目录只读；9 个附件在新导出目录的 annotations 下                                                   |
| 选择了类别就是训练真值吗？                                      | 先保存，再审核，并符合中心/适用/schema 条件，mask 才可能为 1                                          |
| 导出后继续改标签，会更新旧导出吗？                              | 不会。旧导出是快照，要新导出                                                                          |
| unknown 是缺失吗？                                              | 不是。它是“证据不足”的真实类别；missing 才是没有当前答案                                              |
| mask=0 表示类别是 0 吗？                                        | 完全不同。mask=0 表示这个字段不计损失；类别 0 可能是一个有效答案                                      |
| not_applicable 能否当 not_ready 训练？                          | 不能。没必要问的问题，不应被造为负例                                                                  |
| 前史无标签会把图像/state 清零吗？                               | 不会。存在的历史观测保留；只有不存在的历史在读取时 padding                                            |
| 总帧数就是训练样本数吗？                                        | 不是。样本只来自中心；还需逐字段判断监督与采样资格                                                    |
| complete 表示动作 approved 吗？                                 | 不是。完成计数与独立动作质量审核分开                                                                  |
| 0.7 的采样比例会修改 loss mask 吗？                             | 不会。抽什么样本与这个样本哪个头能训练是两个问题                                                      |
| head_spec 自动替我改好模型了吗？                                | 没有。它提供结构/类别顺序，模型与 checkpoint 迁移仍需训练端实现                                       |
| 导出 action 已剔除错误动作了吗？                                | 没有。原动作保留，审核在 intervals；BC 需另做动作块筛选                                               |
| annotations 是完整工作项目备份吗？                              | 不是。恢复完整工作流程还需备份 --work                                                                 |
| 目录自包含是否代表任务/单位全部核实？                           | 不代表。媒体不依赖原路径，物理标定和任务协议仍要交付/核实                                             |
| 文档里出现 bc_action_status/reviewer 等名字，实际都有这些列吗？ | 早期研究文档含计划字段。当前动作审核在 reviews 的 status/reason，具名 reviewer、自动 BC mask 等未落地 |

### 18.2 术语速查

| 术语                 | 大白话解释                                               |
| -------------------- | -------------------------------------------------------- |
| episode              | 一段连续轨迹；本工具裁剪后可能是一段完整示教中的局部片段 |
| center               | 当前要模型回答标签的时刻                                 |
| context              | 为中心附带的前后参考数据，不自动成为独立监督             |
| schema               | 标签字典加填写/适用规则                                  |
| stable ID            | 类别的身份证号，删除后不借给新含义使用                   |
| head/logits          | 模型某个问题的分类输出及各选项原始分数                   |
| applicability        | 现在问这个问题有没有意义                                 |
| required             | 要宣称标注完成时，这个问题是否必须答                     |
| review               | 人工审核；要分清语义标签审核与动作质量审核               |
| loss mask            | 当前答案是否进入损失的开关                               |
| sampling weight      | 抽样时被抽到的相对机会大小                               |
| provenance           | 这条标注依据什么、用什么规则/配置产生的来历记录          |
| source key           | 原始源 UUID 与源帧组成的身份，用来追溯和去重             |
| split group          | 应放在同一训练/验证/测试集合的一组来源                   |
| fingerprint/checksum | 由内容计算的指纹，帮助发现换文件、缺文件或文件变化       |
| PTS                  | 视频帧的展示时间；此导出 source_pts 用秒表示             |
| causal/因果输入      | 预测当前时刻只读取当前及允许过去，不偷看之后             |
| BC                   | 行为克隆：让策略模仿被选为目标的示教动作                 |
